# Landing Page Architecture and Operations

This document describes the current pre-launch landing experience and the
backend implementation supporting its business-inquiry flows.

## Purpose and current experience

The homepage serves two audiences while the complete self-service marketplace
is being prepared for launch:

- Companies see a concierge, human-led talent-matching service that is
  available now.
- Talent see an early-access path that directs them to create and improve their
  profile while the full marketplace is being built.
- The self-service app is presented as a preview, rather than as the primary
  way to get a match.
- Company calls to action open working request and scheduling forms backed by
  the API.
- Existing public jobs, talents, case studies, authentication, and dashboard
  routes remain available.

The backend business-inquiry implementation must be deployed with the frontend
for the request and scheduling forms to work.

## Preserved full-launch landing experience

The pre-launch homepage is temporary. The earlier full marketplace landing
components are intentionally preserved until Kairos is fully live:

- `src/components/layout/company-landing.tsx`
- `src/components/layout/job-landing.tsx`

They contain the richer company and talent marketplace presentations,
including live-platform-oriented sections such as jobs, talent, and expertise
discovery. They are no longer rendered by `src/app/page.tsx`, but they must not
be deleted or repurposed while the pre-launch experience is active.

When the platform is ready for full launch, the homepage can switch from
`PrelaunchLanding` and `TalentPrelaunchLanding` back to these preserved
components (or evolved versions of them) using the existing `intent` value:

```tsx
return intent === "talent" ? <JobLanding /> : <CompanyLanding />;
```

Before making that switch, confirm that the marketplace data, authentication,
onboarding, search, job, talent, and company workflows are production-ready.
The concierge inquiry capability may remain available as an additional contact
path after launch.

## Runtime composition

`src/app/layout.tsx` builds the application shell:

1. `AuthProvider` makes the existing authentication session available.
2. `ThemeProvider` provides system-aware light and dark themes.
3. `ClientLayout` adds the shared header, footer, scrolling behavior, cookie
   consent, intent selection, and business-inquiry modals.
4. Google Analytics is loaded globally with measurement ID
   `G-HWKDMPSTMK`.

Inside `ClientLayout`, the providers are nested in this order:

```text
IntentProvider
└── BusinessInquiryProvider
    └── LayoutContent
        ├── Header
        ├── current route
        ├── Footer (except dashboard routes)
        ├── intent modal
        ├── request and scheduling modals
        └── cookie consent (except dashboard routes)
```

The business-inquiry provider is global so calls to action in the header and
company landing page can open the same modal instances. Opening one inquiry
modal closes the other.

## Audience selection

`src/components/providers/intent-provider.tsx` owns the audience intent:

- Valid values are `company` and `talent`.
- The choice is stored in browser storage as `kairos_intent`.
- A first-time visitor sees `ClientIntentModal`.
- Until a visitor chooses, `company` is the default.
- Hydration is deliberately delayed with `useSyncExternalStore` so the server
  and browser do not render different audience variants.

`src/app/page.tsx` is therefore only a switch:

```tsx
return intent === "talent"
  ? <TalentPrelaunchLanding />
  : <PrelaunchLanding />;
```

The shared header also reads the intent. Company visitors get the concierge
request action, while talent visitors get the app onboarding action.

## Company journey

`src/components/layout/prelaunch-landing.tsx` is the company/default
experience. Its sections are:

1. A pre-launch hero with a primary "Send Us Your Scope of Work" action.
2. The four-step manual process: request, review, sourcing, and introduction.
3. The audiences Kairos serves.
4. Representative talent categories. These are examples, not a claim of live
   public inventory.
5. A clearly labelled self-service platform preview.
6. The reasons to use Kairos, trust signals, mission, vision, and founders.
7. Final actions to submit a request or schedule a call.

Platform preview links are generated by `src/lib/app-links.ts` and go to:

```text
https://app.kairosng.com/auth/onboarding?intent=company
```

The hero's progress link currently goes to the app login page. Direct email is
also offered as a fallback at `info@kairosnexusglobal.com`.

### Submit a scope of work

`BusinessRequestModal` collects:

| Field | Required | Limits |
| --- | --- | --- |
| Full name | Yes | 2-120 characters |
| Work email | Yes | Valid email, at most 254 characters |
| Company | No | At most 160 characters |
| Subject | Yes | 5-200 characters |
| Message | Yes | 20-10,000 characters |
| Attachments | No | At most 5 files, 10 MB per file |

The browser accepts PDF, Word, Excel, text, JPEG, PNG, and WebP files. It sends
the form as `multipart/form-data` through `submitBusinessRequest` in
`src/lib/api.ts`.

The modal has form, loading, success, and error states. It cannot be dismissed
while a request is in flight. A failed request remains retryable, but the UI
currently shows a generic error rather than the server's validation detail.

### Schedule a discovery call

`ScheduleCallModal` collects contact details, a 20-5,000 character project
summary, a date, and one of the hourly slots from 9:00 AM through 3:00 PM
Eastern Time.

The selected Eastern wall-clock time is converted to UTC in the browser. The
conversion uses `Intl.DateTimeFormat` and accounts for Eastern daylight-saving
changes. The API receives both:

- `scheduledFor`: an ISO 8601 UTC instant.
- `timezone`: `America/New_York`.

Both browser and server reject past times. The current interface does not
exclude weekends, holidays, already-booked slots, or overlapping calls.

## Talent journey

`src/components/layout/talent-prelaunch-landing.tsx` is intentionally lighter
than the company journey:

1. It explains that the marketplace is in pre-launch.
2. It asks talent to create a profile and complete readiness information.
3. It explains that visibility and matching improve as the platform launches.
4. It links to a clearly labelled product preview.

All primary actions use:

```text
https://app.kairosng.com/auth/onboarding?intent=talent
```

The landing site does not create the talent account itself. Account creation
and profile completion are owned by the separate app at `app.kairosng.com`.

## Frontend API integration

`src/lib/api.ts` creates a shared Axios client. The base URL is:

```text
NEXT_PUBLIC_API_URL
```

and falls back locally to:

```text
http://localhost:7700/api/v1
```

The inquiry endpoints are public and do not require a token. The shared client
will attach `authToken` when one already exists, but the backend controller
does not require authentication.

### Create business request

```http
POST /api/v1/business-inquiries/requests
Content-Type: multipart/form-data
```

Multipart fields:

```text
fullName
workEmail
company
subject
message
attachments (repeated file field)
```

Successful response:

```json
{
  "message": "Request received",
  "data": {
    "requestId": "uuid",
    "customerSuccessHandoff": true
  }
}
```

### Create call booking

```http
POST /api/v1/business-inquiries/call-bookings
Content-Type: application/json
```

Example body:

```json
{
  "fullName": "Ada Example",
  "workEmail": "ada@example.com",
  "company": "Example Co",
  "projectSummary": "We need a product designer for a six-week engagement.",
  "scheduledFor": "2026-08-03T14:00:00.000Z",
  "timezone": "America/New_York"
}
```

Successful response:

```json
{
  "message": "Your call is scheduled",
  "data": {
    "bookingId": "uuid",
    "scheduledFor": "2026-08-03T14:00:00.000Z",
    "timezone": "America/New_York",
    "customerSuccessHandoff": true
  }
}
```

The common response envelope is produced by the backend's
`ResponseUtilsService`.

## Backend implementation

The server implementation is in the sibling `backend` repository:

```text
src/modules/business-inquiries/
├── business-inquiries.controller.ts
├── business-inquiries.module.ts
├── business-inquiries.service.ts
└── dto/
    ├── create-business-request.dto.ts
    └── create-call-booking.dto.ts
```

`BusinessInquiriesModule` is registered in `src/modules/index.ts`.

Nest's global `ValidationPipe` transforms values and rejects non-whitelisted
fields instead of silently accepting them. The DTOs trim string inputs and
enforce the same principal lengths used by the browser. Server validation is
authoritative.

For attachments, `FilesInterceptor` uses in-memory Multer files. It enforces
five files and 10 MB per file and checks MIME types. The buffers are not stored
in the database or object storage: they are passed directly to the internal
notification email. Only filename, MIME type, and byte size are persisted.

### Request processing

For a business request, the service:

1. Creates a `BusinessRequest` row before sending email.
2. Emails the configured customer-success address, including attachments.
3. If that handoff fails, records `notificationError` and returns a server
   error to the visitor.
4. If it succeeds, records `customerSuccessNotifiedAt`.
5. Sends a confirmation email to the submitter.
6. Records `submitterNotifiedAt`, or logs and stores the confirmation failure.
7. Returns success as long as customer success received the request.

This distinction is important: failure of the visitor's confirmation email
does not make a successfully handed-off inquiry fail.

Call bookings use the same persistence-and-email sequence without attachments.
The backend also checks that the instant is in the future and that the supplied
IANA timezone is valid. It does not independently enforce Eastern business
hours or check calendar availability.

### Persistence

The Prisma migration
`prisma/migrations/20260724090000_add_business_inquiries/migration.sql`
creates:

- `BusinessRequest`, indexed by `workEmail` and `createdAt`.
- `CallBooking`, indexed by `workEmail`, `scheduledFor`, and `createdAt`.

Both tables store delivery timestamps and the last notification error. There
is no status enum, assignment, retry count, or admin management interface yet.

## Configuration and deployment

Landing-page environment:

```dotenv
NEXT_PUBLIC_API_URL=https://<api-host>/api/v1
```

Backend environment:

```dotenv
DATABASE_URL=postgresql://...
RESEND_API_KEY=...
RESEND_MAIL=no-reply@your-verified-domain.example
CUSTOMER_SUCCESS_EMAIL=info@kairosnexusglobal.com
VERSION=v1
PORT=7700
```

If `CUSTOMER_SUCCESS_EMAIL` is missing, the service currently falls back to
`kairosnexuspartner@gmail.com`. Production should always set it explicitly.

The API CORS allowlist must contain the deployed landing-page origin. It
currently includes the production, app, stage, Netlify stage, and local
development origins defined in `backend/src/main.ts`.

Deploy in this order:

1. Configure Resend and customer-success environment variables.
2. Apply the Prisma migration.
3. Deploy the backend with `BusinessInquiriesModule` registered.
4. Confirm both endpoints through Swagger at `/api/doc` or an API client.
5. Set `NEXT_PUBLIC_API_URL` and deploy the landing site.
6. Submit a test request and call booking and verify the database rows plus
   both internal and submitter emails.

## Maintenance notes

- Keep client and DTO validation limits synchronized.
- Changing attachment types requires updating both the input's `accept`
  attribute and the backend MIME allowlist.
- Changing scheduling hours requires updating the frontend slots and adding
  equivalent server validation if the hours must be trusted.
- The current implementation has no CAPTCHA, endpoint-specific throttling,
  malware scanning, or duplicate suppression. Add abuse controls before
  promoting the forms heavily.
- Email is the operational queue. Database rows provide an audit trail, but
  there is no customer-success dashboard or automatic retry worker.
- Attachments exist only in the notification email after the request finishes;
  losing that email means the database metadata cannot reconstruct the files.
- Public platform data elsewhere on the site may still come from API endpoints
  or static/demo data. The pre-launch homepage deliberately avoids presenting
  those examples as complete live inventory.
